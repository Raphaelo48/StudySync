# Архитектура StudySync

Документ описывает принятые решения, схему данных, алгоритмы и форматы.
Всё, что здесь написано, подтверждено кодом и тестами (`tests/`).

## 1. Слои

```
Экраны (app/*)            — только UI и оркестрация действий пользователя
  ↓ используют
Контексты (src/state/*)   — БД, настройки, тема, тосты, таймер (React-состояние)
  ↓ используют
Бизнес-логика (src/logic/*) — чистые функции: валидация, планер, таймер, аналитика, бэкап
  ↓ используют
Репозитории (src/db/repos/*) — SQL-запросы и маппинг строк ↔ модели
  ↓ используют
SqlDriver (src/db/driver.ts) — интерфейс доступа к SQLite
  ├─ drivers/expoDriver.ts  — expo-sqlite (приложение)
  └─ tests/support/sqljsDriver.ts, expoSqliteMock.ts — SQL.js (тесты, реальный SQLite)
```

Правила: UI не содержит SQL; бизнес-логика не знает о React; репозитории не содержат
продуктовых эвристик. Каждая сущность имеет стабильный UUID v4.

## 2. Время и временные зоны

- Хранение: `INTEGER` — миллисекунды с эпохи Unix (не зависит от зоны).
- Отображение и «день/неделя/месяц»: локальная зона устройства (конструкторы `Date`).
- Все сравнения «сегодня/просрочено» — через `startOfDay(now)` локальной зоны.
- События, переходящие через полночь, корректно учитываются в занятости обоих дней
  (обрезка интервала границами дня).

## 3. Схема SQLite (миграция v1)

Таблицы: `subjects`, `tasks`, `subtasks`, `events`, `study_sessions`, `user_settings`,
`goals`, `timer_state`, `plan_history`, `data_backups`, `schema_migrations`.

Ключевые связи и ограничения:

- `tasks.subject_id → subjects.id ON DELETE SET NULL` (задачи не теряются при удалении предмета);
- `subtasks.task_id → tasks.id ON DELETE CASCADE`;
- `events.subject_id → subjects.id ON DELETE SET NULL`; `events.task_id → tasks.id ON DELETE CASCADE`;
- `study_sessions.task_id/subject_id → ... ON DELETE SET NULL` (история сессий переживает удаление задач);
- `goals.subject_id → subjects.id ON DELETE CASCADE` (цель предмета умирает с предметом — предупреждаем в UI);
- CHECK-ограничения: непустые `trim()`-названия, `end_at > start_at`, `planned_minutes > 0`,
  `active_seconds > 0`, перечисления статусов/приоритетов/сложностей, диапазоны настроек;
- индексы: `tasks(status)`, `tasks(deadline_at)`, `tasks(subject_id)`, `tasks(scheduled_start_at)`,
  `events(start_at)`, `events(series_id)`, `events(task_id)`, `study_sessions(started_at/task_id/subject_id)`,
  `subtasks(task_id)`, `goals(subject_id)`, `plan_history(created_at)`, `data_backups(created_at)`;
- строки-синглтоны `user_settings(id=1)` и `timer_state(id=1)` создаются при открытии БД;
- `PRAGMA foreign_keys = ON` выполняется при каждом открытии и **проверяется** чтением
  `PRAGMA foreign_keys` (тест «внешние ключи действительно включены»).

Миграции: список `MIGRATIONS` с версиями; неприменённые выполняются в транзакции,
факт фиксируется в `schema_migrations`. Существующие миграции не редактируются.

### События и повторения

Повторы материализуются: серия = набор строк `events` с общим `series_id` и правилом
в `recurrence_json` (`{freq: 'daily'|'weekly', daysOfWeek?, until?, count?}`).
Плюсы: единообразные конфликты/уведомления/календарь без «виртуальных» сущностей.
Редактирование серии: «только это событие» или «вся серия (будущие)». Удаление — три варианта
с явным подтверждением. Горизонт материализации без `until` — 16 недель, лимит 400 инстансов.

### Учебные блоки плана

План создаёт события `kind='study'` с `task_id` и проставляет задачам
`scheduled_start_at/scheduled_end_at`. Применение обратимо: `plan_history` хранит JSON плана
и id созданных событий; откат удаляет блоки и снимает метки расписания.

## 4. Таймер (восстановление по меткам времени)

Состояние (`timer_state`) хранит: `status`, `phase`, `phase_started_at`, `work_index`,
`accumulated_work_ms`, `accumulated_break_ms`, плановые длительности.

- Активное время = закоммиченные отрезки + текущий running-отрезок; **пауза не начисляет время**.
- `advanceTimer(state, now)` при возврате в приложение (и после закрытия) достраивает фазы:
  завершённый рабочий цикл фиксируется ровно плановой длительностью; перерыв дотекает;
  следующий рабочий цикл **не стартует автоматически** (нет накрутки фиктивных циклов).
- Завершение сессии < 60 с активного времени не создаёт запись StudySession.
- Секундный интервал в UI — только для перерисовки; источник истины — метки времени.

## 5. Алгоритм перепланировщика (детерминированная эвристика)

Приоритизация — многоуровневый компаратор (каждый уровень только при равенстве предыдущего):

1. Класс срочности: 0 — просроченные, 1 — дедлайн в горизонте, 2 — дальше горизонта/без дедлайна;
2. более ранний дедлайн;
3. более высокий приоритет пользователя (3 > 2 > 1);
4. более длительная задача («сначала крупные камни»);
5. более высокая сложность;
6. лексикографический id (детерминизм).

Размещение — жадное по свободным интервалам: учебное окно каждого дня горизонта минус
занятые события и уже размещённые задачи, минус пауза `breakBetweenTasksMin` после каждой
размещённой задачи. Задача атомарна, нормализуется к минимуму 5 минут. Задача с дедлайном
размещается только если завершается до дедлайна.

Гарантии (проверяются `validatePlan` в каждом расчёте и тестами): нет пересечений задач
между собой и с занятыми интервалами; нет отрицательных интервалов; всё внутри учебного окна
и горизонта; перегруз выявляется (`overloaded`, `unplaced` с причинами и предложениями).
Алгоритм не изменяет данные: применение — отдельная транзакционная операция с подтверждением.

## 6. Уведомления

- Идентификаторы детерминированы: `event-start:<eventId>`, `task-deadline:<taskId>`,
  `timer-phase:current`. Перед планированием старый идентификатор отменяется → нет дубликатов.
- Любая правка/удаление события или задачи синхронизирует связанные уведомления.
- Отказ ОС (`denied`, `canAskAgain=false`), недоступность модуля, веб — не ошибки:
  планирование пропускается, приложение работает; пользователь видит понятное сообщение.
- Доставка не гарантируется при ограничениях ОС — текст настроек честно это сообщает.
- Совместимость с Expo Go (Android): модуль `DevicePushTokenAutoRegistration.fx` библиотеки
  при импорте регистрирует push-токен и в Expo Go бросает исключение (push удалён из Expo Go
  в SDK 53). StudySync не использует push-токены, поэтому `metro.config.js` подменяет этот
  side-effect-модуль пустым (`resolveRequest → { type: 'empty' }`). Локальные уведомления
  (разрешения, планирование, отмена) не затрагиваются и работают в Expo Go; проверено
  сборкой бандла и отсутствием кода модуля в нём.

## 7. Экспорт / импорт / резервные копии

Формат: `{format:'studysync-backup', formatVersion:1, exportedAt, appVersion, data:{...}}`.
Все сущности в camelCase, время — epoch ms. zod-схемы: неизвестные поля отбрасываются,
отсутствующие необязательные получают дефолты, некорректные обязательные — ошибка с путём.
Версия формата выше поддерживаемой — явный отказ. Межполевые проверки (end > start и т.п.).

Импорт: одна транзакция; режимы `merge` (дубликаты по id пропускаются и попадают в отчёт)
и `replace` (перед заменой автоматически создаётся внутренняя копия в `data_backups`).
Битые внешние ссылки чинятся на `null` с предупреждением. Любая ошибка записи → откат,
исходные данные целы (тест с дублирующимся id предмета).

Экспорт-файл содержит личные данные — UI предупреждает о бережном хранении.

## 7.1 Импорт расписания КГЭУ

- Источник: публичные эндпоинты личного кабинета `kabinet.kgeu.ru`
  (`/api/raspGrouplist`, `/api/Rasp/ListYears`, `/api/Rasp?idGroup=…`) — авторизация не требуется,
  пароли в приложении не хранятся. Формат ответа зафиксирован zod-схемами (`src/logic/kgeuClient.ts`).
- Разбор строк и дифф — чистые функции (`src/logic/kgeuImport.ts`): настенное время парсится
  в локальную зону вручную (без UTC-сдвига), префиксы дисциплин («л», «пр», «лр»…) маппятся
  в вид занятия, подгруппы и замены отражаются в названии/заметках.
- Происхождение событий: миграция v2 добавила `events.source` ('manual' | 'kgeu') и
  `events.source_ref` ('<groupId>:<код строки>'). Синхронизация удаляет/обновляет ТОЛЬКО
  события с source='kgeu' своей группы; ручные события неприкосновенны (тесты).
- Применение — одна транзакция; уведомления пересинхронизируются после коммита.
- Предметы: уникальные названия дисциплин сопоставляются существующим предметам
  (нормализация: trim + lowercase); недостающие создаются с цветами палитры внутри той же
  транзакции; события связываются с предметом. Повторный импорт дубликатов не создаёт
  (`subjectsCreated` в отчёте), удаление импорта предметы не удаляет.
- Запросы выполняются только по действию пользователя; неофициальный API может измениться —
  ошибки формата/сети показываются понятными сообщениями, частичных изменений не бывает.

## 8. Безопасность и приватность

- Секретов в коде нет. Ядро приложения работает офлайн; сеть используется только
  импортом публичного расписания КГЭУ и только по явному действию пользователя,
  без фонового опроса. Логины и пароли приложение не запрашивает.
- Логгер не пишет пользовательские данные (только технические сообщения и id).
- Сброс данных — двойное подтверждение + автоматическая внутренняя копия + возможность
  восстановления из списка копий.

## 9. Тестирование

- Логика и БД: реальный SQLite (SQL.js/WASM) через тот же интерфейс `SqlDriver`:
  FK, транзакции с откатом, CHECK, миграции, «перезапуск приложения».
- Навигация и экраны: `expo-router/testing-library` (`renderRouter`) с моком expo-sqlite —
  реальное дерево приложения, переходы по вкладкам, сквозное создание задачи через форму.
- Уведомления: fake-клиент (разрешение granted/denied/unsupported).
- Планер: фиксированное «сейчас», проверка инвариантов и порядка, перегруз, отмена применения.
